## 실험 규약 (2026-07-30 확정, 반드시 준수)

이걸 지키지 않은 결과는 폐기 대상이다. 실측으로 확인했다.

| 항목 | 규약 |
|---|---|
| 환경 | Point-LIO → **`srcoff`** / FAST-LIO → **`srcfl`**. 둘 다 `unset CYCLONEDDS_URI` 포함 |
| 재생 | **`-r 0.5`** |
| 반복 | 설정당 **최소 3회** |
| 주 지표 | **z RMSE** (Point-LIO 반속 3회 17.0 ± 0.3 mm, 변동 2%) |
| 참고 지표 | 루프 클로저 (변동 42% — 20% 미만 차이 판정 불가) |

```bash
echo "alias srcoff='source ~/unitree_ros2/cyclonedds_ws/install/setup.bash && source ~/catkin_point_lio_unilidar/install/setup.bash && unset CYCLONEDDS_URI'" >> ~/.bashrc
echo "alias srcfl='source ~/unitree_ros2/cyclonedds_ws/install/setup.bash && source ~/fastlio_ws/install/setup.bash && unset CYCLONEDDS_URI'" >> ~/.bashrc
source ~/.bashrc
echo "[$CYCLONEDDS_URI]"      # 빈 대괄호여야 함
```

**별칭을 알고리즘별로 나눈 이유:** `srcoff` 는 Point-LIO 워크스페이스만 source 하므로
FAST-LIO 를 띄우면 `Package 'fast_lio' not found` 로 조용히 실패한다(2026-07-30 실측).
`unitree_ros2` 는 bag 의 `/lowstate` 가 `unitree_go` 타입이라 양쪽 모두에 필요하다.

**새 터미널마다 `source ~/.bashrc` 가 필요할 수 있다.** 별칭 추가 직후 열린 창은
갱신본을 읽지 않았을 수 있다.

**노드 생존 확인을 습관화할 것.** source 누락이면 노드가 아예 안 뜨는데 재생은
정상 진행되어 4분을 통째로 버린다.

```bash
ros2 node list | grep -E "laser|l1_imu"
```

`CYCLONEDDS_URI` 가 설정된 상태로 로컬 재생하면 메시지가 유실된다. 심하면 재생
프로세스는 살아 있는데 구독자가 아무것도 못 받는다. 근거는 R00 §1.5.

**이전에 이 규약 없이 얻은 결과는 모두 폐기했다.**

### 3번 — FAST-LIO config 정리 (완료 2026-07-30)

**우려했던 상황은 아니었다.** 리포지토리 원본 6개(`avia`, `go2_l1`, `horizon`,
`mid360`, `ouster64`, `velodyne`)는 7/24 빌드 때 `--symlink-install` 로 만들어져
이미 심볼릭 링크였다. `cp` 와 `nano` 는 링크를 따라가므로, `install` 경로를
편집한 것처럼 보였던 작업도 내용은 전부 `src` 에 기록돼 있었다.

→ **`go2_l1.yaml` 로 얻은 기존 결과는 config 추적이 가능하며 폐기 대상이 아니다.**

나머지 8개는 7/28~29 에 홈 디렉터리에서 `cp` 로 밀어넣은 일반 파일이었다.
git 밖이고 `src` 를 고쳐도 반영되지 않는 상태였다. `src` 에만 있던 3개
(`go2_l1_tuned`, `go2_l1_lidar_imu`, `go2_l1_indoor`)는 반대로 `install` 에 없어
**로드 자체가 불가능**했다 — 편집해도 아무 효과가 없었을 파일들이다.

정리 결과 `config/` 에는 정본 `go2_l1.yaml` + 리포지토리 원본 5개만 남기고,
폐기 이력 10개는 `config/archive/` 로 옮겨 git 에 남겼다.

```bash
# install 의 일반 파일(=고아)만 archive 로. 심볼릭 링크는 건드리지 않는다
cd ~/fastlio_ws/install/fast_lio/share/fast_lio/config
for f in *.yaml; do
  [ -L "$f" ] || mv -v "$f" ~/fastlio_ws/src/FAST_LIO/config/archive/
done
```

**launch 기본값이 `mid360.yaml` 이다.** 인자 없이 실행하면 Livox 설정이 로드돼
Go2 데이터를 한 점도 못 받는다. `config_file:=` 를 **항상 명시할 것.**

```bash
grep -n "config_file" ~/fastlio_ws/src/FAST_LIO/launch/mapping.launch.py
# 34: 'config_file', default_value='mid360.yaml',
```

정리 후 확정된 두 config. **차이는 `imu_topic` 한 줄뿐이다.**

| | config | `imu_topic` | 나머지 |
|---|---|---|---|
| before | `go2_l1_before.yaml` | `/utlidar/imu` | 동일 |
| after | `go2_l1.yaml` | `/l1_imu_fixed` | 동일 |

**FAST-LIO 오도메트리 토픽은 `/Odometry`** (`laserMapping.cpp` 934행). Point-LIO 의
`/aft_mapped_to_init` 과 다르므로 `dump_odom.py` 에 3번째 인자로 넘겨야 한다.
**rviz 기본값이 `true`** 이므로 반복 실행 시 `rviz:=false` 를 붙인다.

#### 남은 문제 — after z RMSE 306 mm

**런북 판정 기준으로 "실패"(>100 mm) 구간이다.** 같은 bag·같은 규약에서
Point-LIO 는 17.0 ± 0.3 mm 였으므로 **18배 차이**다.

변동이 3.6% 로 작아 우연이 아니라 설정에 구조적 원인이 있다. 유력한 후보는
**`feature_extract_enable: true`** 다. 이 데이터는 스캔당 4,143점을 18라인으로
나누면 라인당 230점 남짓이라 특징 추출에 여유가 없다. Point-LIO 는 원시 점을
그대로 쓰므로 이 제약이 없다.

**`feature_extract_enable: false` 를 검증했고 기각됐다 (2026-07-31, 각 3회).**

| 지표 | `true` (정본) | `false` | 판정 |
|---|---|---|---|
| **z RMSE** | **306.5 ± 10.9 mm** | **351.0 ± 12.0 mm** | **유의하게 악화** |
| 루프 클로저 | 0.663 ± 0.642 m | 0.454 ± 0.247 m | 변동에 묻힘 |
| 수평 RMS | 0.926 ± 0.187 m | 0.828 ± 0.048 m | 변동에 묻힘 |
| 총거리 | 44.63 ± 1.34 m | 44.47 ± 0.38 m | 변동에 묻힘 |
| No Effective Points | 0 | 0 | — |

차이 44.5 mm 는 각 그룹 표준편차(11, 12 mm)보다 크므로 유의하다. **기대와 정반대다.**
지면 점이 대부분인 이 환경에서는 곡률 기반 선별이 오히려 좋은 점을 골라내는 역할을
한 것으로 보인다. `feature_extract_enable: true` 를 유지한다.

설정은 `config/go2_l1_nofeat.yaml` 로 남겨 둔다(archive 로 옮기지 않는다). 11번에서
재사용하고 이 결과를 재현할 수 있어야 한다.

**306 mm 의 원인은 아직 미상이다.** 남은 후보:

- `extrinsic_T: [0.007698, 0.014655, -0.00667]` — 실제 L1-IMU 오프셋과 맞는지 미검증
- `point_filter_num: 1` — 다운샘플 없이 전량 사용
- `filter_size_surf` / `filter_size_map` — 복셀 크기
- **알고리즘 구조 차이 자체** — 스캔 단위 vs 포인트 단위. 이 경우 설정으로 해결 불가

11번(세 알고리즘 재비교)에서 다룬다.

#### 촬영 시 겪은 함정

- **웨일랜드에서는 `x11grab` 으로 창을 잡을 수 없다.** 로그인 화면 톱니바퀴에서
  "Ubuntu on Xorg" 선택 후 재로그인해야 `rec_rviz.sh` 가 동작한다
- **`x11grab` 은 창이 아니라 화면 영역을 찍는다.** RViz 위에 터미널·브라우저가
  겹쳐 있으면 그대로 녹화된다. 듀얼 모니터라면 **RViz 는 외부 모니터에 최대화,
  터미널은 노트북 화면**에 두는 것이 확실하다

```bash
WID=$(wmctrl -l | grep -i rviz | head -1 | awk '{print $1}')
wmctrl -i -r $WID -b add,maximized_vert,maximized_horz
```

- **녹화 창(ffmpeg)을 클릭하지 말 것.** 아무 키나 눌리면 즉시 종료된다
  (52초에서 끊긴 회차가 있었다)
- **A 와 B 의 창 크기·시점·표시 설정이 같아야 C 가 성립한다.** launch 를 새로
  띄우면 초기화되므로 매번 다시 맞춘다
- **B 는 `-r 0.5` 로 찍고 후처리에서 4배속**한다. 실시간 재생은 메시지 유실로
  궤적이 실제보다 나빠 보인다

```bash

cd ~/fastlio_ws/videos
ffmpeg -i divergence_raw.mp4 -i fixed_full.mp4 \
  -filter_complex "[0:v]trim=0:20,setpts=PTS-STARTPTS,scale=1280:-2[l];
                   [1:v]trim=0:80,setpts=0.25*PTS,scale=1280:-2[r];
                   [l][r]hstack" \
  -c:v libx264 -crf 22 -pix_fmt yuv420p -y compare.mp4
```

#### 판단 메모 — 점 개수로 누적 여부를 판정하지 말 것

B 촬영 중 "지도가 안 쌓이고 위치만 바뀐다"고 의심했으나, 프레임 간 **점 유지율**을
재보니 89~100% 로 정상 누적이었다. 방이 작아(최대 사거리 2.4~5.6 m) 초반 몇 스캔만으로
화면이 채워지므로 **점 개수는 곧 정체된다.** 개수가 아니라 지속성을 봐야 한다.

`CloudRegistered` 는 현재 스캔만 표시하므로 매 프레임 통째로 교체된다. 이것이 눈에

### 브리지 (`gnss_bridge.py`)

`/gnss` 는 `std_msgs/String` 에 JSON 을 담아 발행한다.

```
{"fixed":1,"hdop":0.800000,"longitude":127.264220,"latitude":37.011434,
 "satellite_total":12,"satellite_inuse":9,"timestamp":1785397828}
```

`robot_localization` 의 `navsat_transform_node` 는 `sensor_msgs/NavSatFix` 를
요구하므로 변환이 필요하다. `/gnss` → **`/gps/fix`**.

| 설계 | 내용 |
|---|---|
| 공분산 | `sigma_h = HDOP × UERE`, UERE 기본 3.0 m. **EKF 튜닝의 주 손잡이** |
| | HDOP 0.78 → sigma_h 2.34 m (분산 5.48). 키우면 GPS 를 덜 믿는다 |
| 유효 판정 | `fixed==1` **및** 위성 ≥4 **및** `0 < hdop ≤ 5` |
| | `hdop==0.0` 은 유효값이 아니라 측위 실패 시 나오는 값이다(실측) |
| 무효 처리 | `STATUS_NO_FIX` + 공분산 1e3. `navsat_transform_node` 가 무시한다 |
| 고도 | JSON 에 없음 → `NaN` |
| 타임스탬프 | 기본 수신 시각. JSON 의 `timestamp` 는 **1초 해상도인데 발행은 2초 간격**이라 |
| | 어긋난다. EKF 시간 동기가 이상하면 `-p stamp_source:=json` 을 시도 |

## 실외 실측 (2026-07-31) — LIO 단독 불가 확정

상세 수치는 `RESULTS_0731_outdoor.md`. 여기에는 결론과 파급만 적는다.

### 8번(위치·헤딩 검증) 부분 성과

| 항목 | 결과 | 판정 |
|---|---|---|
| 회전축 오차 | **4.1°** | **`R_LB` 검증됨** |

| 연직축 누적 회전 | 505° / 742° | 퇴화 |
| 총 회전량 | 727.9° (2% 오차) | 회전 자체는 감지 |

**축은 맞는데 연직 성분만 68%** — 회전은 봤으나 자세가 흔들렸다는 뜻이다.
`R_LB`·`LEVER` 는 검증됐으므로 **8번의 교정 검증 목적은 달성**했다.
다만 실내에서 다시 해야 판정 기준(제자리, heading +360°)을 온전히 적용할 수 있다.

### 교정으로 해결 불가 — 근거

- 최적 yaw 정렬 후에도 잔차 **RMS 89.6 m** (180초 구간). 단일 변환으로 안 맞는다
- 궤적 **모양 자체가 다르다.** 축척·회전 오차가 아니다
- 오차가 t=25 s(이동 시작)부터 **단조 증가** — 적분 표류
- 점군은 정상이다. 오히려 실내보다 사거리가 길다(3.02 m vs 1.81 m)

**문제는 점의 양이 아니라 분포다.** 평면 지면 하나로는 요와 수평 위치를 제약할 수
없다. 실내에서는 벽이 간헐적으로나마 잡아줬으나 운동장에는 없다.
교정은 발산 시각을 늦출 뿐이다.

`R_LB` 의 yaw 성분이 ±수십 deg 불확실한 것도 실외에서만 문제가 된다. 수평 동적가속도
(RMS 0.14 m/s²)가 잘못된 방향으로 이중적분되는데, 실내에서는 벽이 이를 계속
교정해줬기 때문이다. 180초에 125 m 는 가속도 오차 **0.008 m/s²** 에 해당한다.

### 대회 전략 수정

- **GPS 가 주 위치 소스여야 한다.** 실외 실측 HDOP 0.78, 정확도 약 2.4 m
- **LIO 는 국소 장애물 회피와 단기 자세 추정으로 역할 축소**
- **17번(이중 EKF)은 선택이 아니라 필수.** 최우선 과제로 올린다
- 실외에서 LIO 단독 웨이포인트 주행은 불가능하다

2. **`-r 0.5`** 로 재생한다
3. **설정당 3회 반복**하고 평균±표준편차로 판정한다. 단일 실행 비교는 무의미
4. **한 번에 설정 하나만 바꾼다.** 노드 버전 변경도 설정 변경이다
   (실제로 이걸 놓쳐 구버전/수정본 결과를 비교하는 실수를 했다)
5. **LIO 노드는 재생마다 새로 띄운다.** 중력 초기화가 초반 정지 구간에서 한 번만
6. **record → play 순서.** 반대면 메시지 0개로 녹화된다
7. **녹화 직후 `ros2 bag info` 로 Count 확인**
8. **정지검증 로그 확인.** T1 에 `[정지검증] 통과` 가 떠야 한다. 안 뜨면 그 회차 버림
9. **바꾼 설정을 한 줄로 메모**

### 수동 실행 절차 (터미널 4개, 각각 `srcoff`)

```bash
# T1
python3 ~/fastlio_ws/tools/l1_imu_fix.py
# T2
ros2 launch point_lio mapping_unilidar_l1.launch.py
# T3  (회차마다 이름 변경)

```

### 실외 bag 녹화 실패 원인 규명 (2026-07-31)

실외 15분 녹화(`rosbag2_2026_07_30-16_50_28`, 613 MB)에서 정작 필요한 센서가 거의
없었다. **원인이 두 개였고 서로 독립적이다.** 처음에는 대역폭·GPS·압축을 의심했으나
전부 아니었다.

#### 원인 1 — `-a` 의 토픽 발견 실패 (라이다·`/lowstate` 유실의 원인)

`/rosout` 에 이 에러가 **0초부터 944초까지 0.1초 간격으로 4,731번** 찍혀 있다.

```
rosbag2_recorder: Failure in topics discovery.
Error: Something went wrong loading the typesupport library ...
```

`ros2 bag record -a` 는 주기적으로 전체 토픽 목록을 훑으며 하나씩 구독한다.
중간에 타입서포트를 못 불러오는 토픽을 만나면 **그 순회가 통째로 중단**되어,
목록 뒷부분의 토픽은 구독 시도조차 받지 못한다.

구독 시각이 두 무리로 갈린다.

| 무리 | 첫 구독 | 토픽 |
|---|---|---|
| A | 0.0~0.5초 | `/rosout`, `/lowcmd`, `/frontvideostream`, `/lf/sportmodestate`, `/gnss`, `/multiplestate`, `/lf/battery_alarm` |
| B | **942~944초** | `/lowstate`, **`/utlidar/*` 전부**, `/sportmodestate`, `/audiosender`, `/api/uwbswitch/*` |

무리 B 는 942초 이전 구간이 **0개**다. 링크가 멀쩡했어도 받지 못했을 것이다.
942초에 순회가 더 진행된 것은, 문제되던 발행자가 그 무렵 사라져 걸림돌이 없어졌기
때문으로 보인다.

**대역폭 문제가 아니다.** 마지막 3초에 `/lowstate` 가 499 Hz, `/utlidar/cloud` 가
18 Hz 로 정상 수신됐다. 링크는 충분했다.

#### 원인 2 — t=475.5 초에 로봇-노트북 연결이 끊김 (GPS 공백의 원인)

무리 A 토픽이 **전부 동시에** 끊겼다. GPS 만의 문제가 아니었다.

| 토픽 | 0~475초 | 475~940초 | 940~945초 |
|---|---|---|---|
| `/lowcmd` | 233,115 | 720 | 320 |
| `/frontvideostream` | 13,574 | 42 | 79 |
| `/lf/sportmodestate` | 9,505 | 30 | 14 |
| `/gnss` | 475 | 1 | 1 |

0~475초 구간으로 나누면 레이트가 정확히 정상이다(`/lowcmd` 493 Hz, 영상 28.8 fps,
`sportmodestate` 20 Hz). 944초로 나누면 전부 절반이 되어 "대역폭 부족"으로 오독하기 쉽다.

475~940초에 완전 0 이 아니라 **초당 1.5개 수준의 실낱같은 통신**이 남아 있다.
완전 단선이 아니라 **접촉 불량·간헐 연결**에 가깝다.

노트북 내장 랜포트에 유선으로 직결한 상태로 로봇이 운동장을 한 바퀴(356 m) 돌았다.
**실외에서 유선 연결로 로봇을 따라다니며 녹화하는 방식은 성립하지 않는다.**

끊기기 30초 전부터 GPS 좌표가 고정(37.011447, 127.264044)이고 `mode=0`,
속력 0.01 m/s 였다. **한 바퀴를 다 돌고 멈춘 뒤에 연결이 끊긴 것**으로 보인다.

### 이번에 겪은 함정 (2026-07-30)

- **`srcoff` 로 FAST-LIO 를 띄우면 조용히 실패한다.** 워크스페이스가 다르다.
  재생 전 `ros2 node list` 로 노드 생존을 확인할 것. 4분을 통째로 버렸다
- **`tee` 를 빠뜨리면 로그가 0행이 되고, 에러 0회와 구분되지 않는다.**
  `wc -l` 로 로그 행 수를 함께 확인할 것. 회차 하나를 재실행했다
- **`grep -v sportmodestate` 는 오류의 첫 줄만 거른다.** 두 번째 줄(`Error:`)이
  남아 화면이 여전히 홍수가 된다. `2>/dev/null` 이 낫다
- **`ros2 bag play` 에 `--playback-duration` 이 없는 버전이 있다.** `timeout` 으로 대체
