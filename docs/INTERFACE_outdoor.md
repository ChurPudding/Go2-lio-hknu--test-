# 실외 자율주행 — 위치추정 인터페이스

작성 2026-08-02 / 갱신 2026-08-13. 담당: 위치추정·지도·GPS

이 문서는 **실외에서 위치추정 쪽이 무엇을 내보내고, 받는 쪽이 그것을 어떻게
쓰면 되는지**를 정리한 것입니다. 경로계획·추종을 맡은 쪽에서 주로 보시면 되고,
장애물 인식 쪽에서도 5장(신뢰도 신호)은 관련이 있습니다.

배경을 모르셔도 읽을 수 있게 썼습니다. 처음 보는 용어는 부록에 정리해 두었으니
필요할 때 참고해 주세요.

실내 구조는 `docs/INTERFACE_indoor.md` 에 따로 있습니다.

## 1. 실외는 실내와 구조가 다릅니다

### 실내에서 하던 방식

실내에서는 라이다로 주변 벽과 기둥을 보면서 위치를 알아냈습니다.
이걸 **LIO**(라이다-관성 오도메트리)라고 합니다. 복도에서 26 m 를 돌아
제자리로 왔을 때 오차가 0.24 m 였으니 상당히 정확했습니다.

원리는 간단합니다. 벽이 옆에 있으면 "내가 벽에서 1.2 m 떨어져 있다"를 알 수
있고, 앞뒤로 움직이면 벽의 무늬가 흘러가는 속도로 얼마나 갔는지 알 수 있습니다.
**주변에 특징이 있어야 위치를 알 수 있다**는 게 핵심입니다.

### 실외에서는 그게 안 됩니다

7/31 에 운동장에서 356 m 를 주행하며 측정한 결과입니다.

| 방법 | 최종 수평 오차 |
|---|---|
| GPS | 2.4 m |
| LIO (FAST-LIO) | 110 m |
| LIO (Point-LIO) | 26,695 m |
| IMU 단독 | 84,829 m |

LIO 가 완전히 무너졌습니다. 이유는 **점군의 96~99% 가 지면**이었기 때문입니다.
운동장은 사방이 트여 있어서 라이다에 잡히는 게 바닥밖에 없습니다.

평평한 바닥만 보고 있으면 "내가 바닥 위 0.4 m 에 있다"는 알 수 있어도,
**앞으로 갔는지 옆으로 갔는지, 어느 쪽을 보고 있는지는 알 수 없습니다.**
바닥은 어디를 봐도 똑같이 생겼기 때문입니다.

교정으로 해결되지 않는다는 것도 확인했습니다. 최적으로 맞춘 뒤에도 잔차가
89.6 m 였고, 궤적 모양 자체가 달랐습니다.

### 그래서 실외에서는 GPS 를 씁니다

| 역할 | 담당 센서 |
|---|---|
| 지금 어디에 있는가 | GPS |
| 어느 쪽을 보고 있는가 | GPS + IMU (4장 참조) |
| 눈앞에 뭐가 있는가 | 라이다 (장애물 인식 담당) |

**실외에서는 점군 지도를 만들지 않습니다.** GPS 웨이포인트 목록이 곧 경로이고,
장애물은 그때그때 피합니다.

## 2. 좌표계 약속

여러 사람이 만든 코드가 붙으므로 좌표 규약을 먼저 맞춰야 합니다.
ROS 표준(REP-103)을 따릅니다.

**프레임 세 개**

| 프레임 | 뜻 |
|---|---|
| `map` | 출발 지점을 원점으로 하는 고정 좌표계. GPS 로 보정되므로 **튈 수 있음** |
| `odom` | 부드럽게 이어지는 좌표계. 튀지 않지만 시간이 지나면 조금씩 어긋남 |
| `base` | 로봇 몸통 (실내와 동일. URDF 의 루트 링크) |

**둘을 나누는 이유**가 있습니다. GPS 는 정확하지만 1 초에 한 번 갱신되면서
값이 조금씩 튑니다. 이걸 그대로 쓰면 로봇 위치가 순간이동하는 것처럼 보이고,
경로추종기가 놀라서 급격한 명령을 냅니다.

그래서 **`odom` 은 부드럽게, `map` 은 정확하게** 두 개를 유지합니다.

- **속도 제어처럼 부드러움이 중요한 계산** → `odom` 프레임 사용
- **웨이포인트까지 얼마나 남았는지 같은 계산** → `map` 프레임 사용

**축 방향**

- x = 동쪽, y = 북쪽, z = 위
- 각도는 **동쪽이 0°**, 반시계 방향이 +
- 단위는 미터, 초, 라디안

북쪽이 0° 가 아니라는 점에 주의해 주세요. 나침반과 다릅니다.

## 3. 토픽

### 3.1 지금 존재하는 것

아래는 실제로 동작을 확인한 것들입니다. 다만 **주행 담당 쪽에서 직접 쓰실
것은 아닙니다.** 3.2 의 출력이 나오면 그것을 쓰시면 됩니다.

| 토픽 | 타입 | 주기 | 비고 |
|---|---|---|---|
| `/gnss` | `std_msgs/String` | 1 Hz | Go2 원본. JSON 문자열 |
| `/gps/fix` | `sensor_msgs/NavSatFix` | 1 Hz | `tools/gnss_bridge.py` 출력. **검증 완료** |
| `/gps/path` | `nav_msgs/Path` | 1 Hz | `tools/gnss_path.py` 출력. RViz 확인용 |
| `/lowstate` | `unitree_go/LowState` | 500 Hz | Go2 원본. IMU 포함 |
| `/sportmodestate` | `unitree_go/SportModeState` | 약 300 Hz | Go2 원본. 속도·발 위치 |
| `/utlidar/cloud` | `sensor_msgs/PointCloud2` | 15 Hz | 원시 점군 |
| `/utlidar/robot_odom` | `nav_msgs/Odometry` | 150 Hz | Go2 내장 다리 오도메트리 |
| `/wirelesscontroller` | `unitree_go/WirelessController` | 19 Hz | 리모컨 스틱 입력 |

**주의 — `/utlidar/robot_odom` 은 실외에서 위치로 쓸 수 없습니다.**
356 m 주행에서 수평 오차 RMS 10.2 m, 최대 20.0 m 였습니다.

### 3.2 우리가 내보내는 것 — 이름 확정 (2026-08-13)

우리가 만든 토픽은 전부 `/hknu` 밑에 둡니다. Go2 원본(`/utlidar/*`, `/lowstate`)과
섞이지 않고, 죽어 있는 `/uslam/*`, `/lio_sam_ros2/*` 와도 구분됩니다. 대회장에서
`ros2 topic list | grep hknu` 하나로 우리 시스템 전체가 보입니다.

`/hknu` 는 개인이 아니라 **팀 네임스페이스**입니다. 경로계획·장애물 회피 출력도
여기 들어옵니다.

**토픽 이름은 실내·실외를 구분하지 않습니다.** 받는 쪽이 지금 실내인지 실외인지
알 필요가 없어야 하기 때문입니다. 구분되는 것은 실행 스크립트와 노드 이름입니다.

| 토픽 | 타입 | 내용 | 상태 |
|---|---|---|---|
| `/hknu/robot_pose` | `geometry_msgs/PoseWithCovarianceStamped` | 자세 + 공분산. **주 입력** | 1단계 |
| `/hknu/robot_odom` | `nav_msgs/Odometry` | `frame_id=map`, `child=base_link`. 속도 포함 | 1단계 |
| `/hknu/robot_map` | `nav_msgs/OccupancyGrid` | latched. 격자 지도 | 미구현 |
| `/hknu/robot_path` | `nav_msgs/Path` | `frame_id=map`. **경로계획 담당 출력** | 미구현 |

위치와 자세를 나누지 않습니다. `PoseWithCovarianceStamped` 하나에 위치·방위·
공분산이 다 들어갑니다. 나누면 두 메시지의 도착 시각이 어긋나 받는 쪽이 시간
동기를 직접 맞춰야 합니다.

**목표점만 `/hknu` 밖에 둡니다.**

```
/goal_pose        geometry_msgs/PoseStamped    frame_id=map
```

RViz 의 "2D Goal Pose" 버튼이 기본으로 루트 `/goal_pose` 에 발행하기 때문입니다.
지금은 손으로 찍어 시험하는 단계라 설정 없이 바로 쓰는 쪽을 택했습니다.
웨이포인트 공급 노드가 생기면 그때 옮겨도 됩니다.

`PointStamped` 가 아니라 `PoseStamped` 인 것은 도착 방위를 지정할 자리를 남기기
위함입니다. 필요 없으면 무시하시면 됩니다.

**`/clicked_point` 는 쓰지 않습니다.** 대회 자율주행 부문은 경기 중 사람 조작
입력이 금지입니다.

**방위 출력** — 구현 완료, 로봇 검증 전

```
/gps_heading/heading        std_msgs/Float32   절대 방위 [deg]
/gps_heading/heading_info   std_msgs/String    상태 JSON
```

ENU 기준입니다. **동쪽이 0도, 반시계 방향이 +** 입니다. 나침반과 다릅니다.

보통은 직접 쓰실 일이 없습니다. 2단계부터 위 위치 출력에 반영되어 나갑니다.

### 3.2.1 네임스페이스에 넣지 않는 것

| | 이유 |
|---|---|
| `/tf`, `/tf_static` | tf2 리스너는 전역 `/tf` 만 봅니다 |
| 프레임 이름 | `map`, `odom`, `base_link` 는 토픽이 아닙니다 |
| `/utlidar/*`, `/lowstate`, `/api/sport/request` | Go2 가 정한 이름 |
| `/goal_pose` | RViz 기본값 |

노드를 네임스페이스에 넣으면 **TF 토픽까지 `/hknu/tf` 로 딸려 들어갑니다.**
그러면 RViz 와 nav2 가 TF 를 못 찾는데, 에러가 나지 않아 원인을 찾기 어렵습니다.
반드시 되돌려야 합니다.

```bash
--ros-args -r __ns:=/hknu -r /tf:=/tf -r /tf_static:=/tf_static
```

`tools/run_outdoor_loc.sh` 가 이 리매핑을 고정해 두었으니 그걸 쓰시는 편이
안전합니다. 확인:

```bash
ros2 topic list | grep -E '^/tf'      # /tf, /tf_static 만 나와야 정상
```

### 3.2.2 TF 소유권 — 중요

`/tf` 는 여러 노드가 함께 쓰도록 설계된 토픽입니다. **여럿이 발행하는 것 자체는
정상이며 오류가 아닙니다.** 문제가 되는 것은 **같은 부모-자식 쌍**을 둘이 동시에
발행할 때입니다. 두 값이 번갈아 들어와 로봇 위치가 튑니다.

| 상황 | 결과 |
|---|---|
| Go2 가 `odom→base_link`, 우리가 `map→odom` | 정상 |
| Go2 와 우리가 둘 다 `odom→base_link` | 튐 |
| `go2_nav_interface.py` 와 스텁이 둘 다 `map→odom` | 튐 |
| AMCL / slam_toolbox 가 함께 떠 있음 | 튐 |

연결선마다 주인은 하나입니다.

| 연결선 | 주인 |
|---|---|
| `map → odom` | 실외: `localization_stub.py` / 실내: `go2_nav_interface.py` — **동시 실행 금지** |
| `odom → base_link` | Go2 내부 |

`localization_stub.py` 는 발행 시작 전 2초간 `/tf` 를 엿들어 같은 연결선의 주인이
이미 있는지 확인하고, 있으면 그 TF 를 발행하지 않습니다. 그래도 실행 순서에 따라
빠져나갈 수 있으니 확인은 직접 하시는 편이 좋습니다.

```bash
ros2 run tf2_tools view_frames
```

### 3.2.3 실내 파이프라인과의 관계

| | 실내 | 실외 |
|---|---|---|
| 실행 | `run_indoor.sh` | `run_outdoor_loc.sh` |
| 노드 | `go2_nav_interface.py` | `localization_stub.py` |
| 위치 소스 | Point-LIO (`/indoor/base_pose`) | 다리 오도메트리 (`/utlidar/robot_odom`) |
| 토픽 이름 | `/map`, `/odom`, `/scan` (Nav2 기본) | `/hknu/*` |
| `map→odom` | 항등 | 축척 오차 상쇄 |

실내가 Nav2 기본 이름을 쓰는 것은 Nav2 가 그 이름을 기대하기 때문입니다.
실외는 Nav2 를 쓰지 않으므로 `/hknu` 규칙을 따릅니다.

**둘을 동시에 띄우지 마십시오.**

### 3.2.4 축척 계수 k

다리 오도메트리는 이동 거리를 실제보다 약 20% 짧게 셉니다. 발 미끄러짐과 발바닥
변형 때문입니다.

```
실제 거리 = k x 오도메트리 거리
```

폐루프 시험으로는 잡히지 않습니다. 궤적 전체가 같은 비율로 줄어들면 모양은
그대로라 출발점에 정확히 돌아오기 때문입니다. 축소 복사한 지도와 같습니다.
반드시 줄자나 위성지도 같은 **외부 기준**이 필요합니다.

노면에 따라 값이 다릅니다. `tools/go2_calib.py` 에서 관리합니다.

| 상수 | 값 | 근거 |
|---|---|---|
| `K_INDOOR` | 1.1995 | 실내 타일 줄자 51.83 m, 6회, 편차 0.33 m |
| `K_OUTDOOR` | 1.23 | 운동장 둘레 325 m, 위성지도 대조 |

GPS 정렬로 얻은 1.1910 / 1.2327 은 교차검증용입니다. GPS 좌표의 초 단위 떨림이
이동거리로 더해져 경로가 부풀려지므로, 이 방법은 축척을 실제보다 크게 냅니다.

**원시 `/utlidar/robot_odom` 이나 `/sportmodestate` 를 위치로 직접 쓰시면 안
됩니다.** 축척이 보정되지 않은 값입니다. `/hknu/` 가 붙은 쪽이 보정본입니다.

k 를 다시 재려면:

```bash
python3 tools/odom_scale_check.py <5m_직진_bag> --truth 5.00
```

겨울 눈 노면에서는 재검증이 필요합니다. 미끄러지면 k 가 커집니다.

### 3.2.5 지금 되는 것과 안 되는 것

| | 1단계 (현재) | 2단계 앵커링 | 3단계 GTSAM |
|---|---|---|---|
| 상대 목표 주행 | O | O | O |
| GPS 웨이포인트 | **X** | O | O |
| 드리프트 보정 | 없음 | 없음 | 있음 |

1단계의 `map` 원점은 부팅 지점이고 `+x` 는 부팅 시 IMU yaw 입니다. 지구와 아무
관계가 없으므로 **위경도 웨이포인트를 `map` 좌표로 변환할 수 없습니다.** 2단계에서
GPS 원점과 진북에 고정하면 해결됩니다.

IMU yaw 표류(분당 2~5도)도 1단계에서는 보정하지 않습니다. 4장 참조.

## 4. 방향(heading)에 관한 주의사항

이 부분이 실외에서 가장 까다로운 지점이라 따로 설명드립니다.

### Go2 는 나침반이 없습니다

조사 결과 Go2 의 방향값은 **자이로스코프를 적분해서 만든 값**이었습니다.
자이로는 "얼마나 빨리 돌고 있는가"를 재는 센서라, 이걸 계속 더하면 "지금까지
얼마나 돌았는가"가 나옵니다.

문제가 두 가지입니다.

**첫째, 기준이 없습니다.** 전원을 켠 순간의 방향이 0° 입니다. 북쪽이 아닙니다.
로봇을 껐다 켜면 기준이 바뀝니다.

**둘째, 시간이 지나면 어긋납니다.** 측정해 보니 **분당 2~5°** 씩 틀어졌습니다.
5 분이면 10~25° 입니다. 코스 폭이 3 m 라면 금방 벗어나는 크기입니다.

게다가 이 값이 같은 날 안에서도 세 배까지 변했습니다. 미리 보정값을 정해두는
방식으로는 해결되지 않습니다.

### GPS 로 계속 고쳐 나갈 예정입니다

로봇이 앞으로 걸어가면, GPS 위치가 이동한 방향이 곧 로봇이 향한 방향입니다.
이걸로 자이로의 어긋남을 계속 되돌립니다.

오프라인 분석에서 5 m 를 이동한 두 지점으로 계산했을 때 **오차 약 8°** 였습니다.
개별 값은 부정확하지만 계속 들어오므로 평균 내면 훨씬 정확해집니다.

**이 부분은 만들어서 검증까지 마쳤습니다.** 녹화해 둔 실외 주행 데이터로
확인한 결과, 방향 오차가 **약 2°** 수준으로 유지됐습니다. 코스 반지름을
20 m 로 놓으면 옆으로 0.8 m 어긋나는 정도이고, GPS 자체 오차(2.4 m)보다
작습니다.

```
[  실제 로봇에서의 동작 확인 (미완료)  ]
```

**그런데 이 방법에는 사각지대가 있습니다.**

| 상황 | 방향 보정 |
|---|---|
| 직진 중 | 잘 됨 |
| 정지 중 | **불가** — 이동이 없으니 방향을 알 수 없음 |
| 제자리 회전 중 | **불가** |
| 옆으로 걸을 때 | 부정확 |

즉 **오래 멈춰 있거나 제자리에서 많이 돌면 방향 정확도가 나빠집니다.**
30 초 정지에 1~2.5° 정도입니다.

### 로봇이 왼쪽으로 조금씩 밀립니다

측정 중에 하나 더 발견했습니다. **이 로봇은 걸을 때 몸통이 향한 방향보다
평균 1.21° 왼쪽으로 이동합니다.**

사족보행 로봇은 자동차와 달리 몸통이 정면을 보면서도 비스듬히 이동할 수
있습니다. 그 각도를 측면미끄러짐각이라고 하는데, 이 로봇은 그 값이 늘 같은
쪽으로 치우쳐 있었습니다. 우연이 아니라는 것도 확인했습니다.

크기로 보면 100 m 를 걸을 때 옆으로 2.1 m 밀리는 정도입니다.

`/sportmodestate` 에 로봇의 전후·좌우 속도가 이미 들어 있어서, 이걸로 계산해
빼면 됩니다. 위치추정 쪽에서 처리할 예정이라 **주행 담당 쪽에서 따로 하실 일은
없습니다.** 다만 로봇에 이런 성질이 있다는 것만 알아두시면 좋겠습니다.

경로추종을 만드실 때 로봇이 목표선에서 한쪽으로 꾸준히 벗어나는 현상을
보신다면, 원인이 제어기가 아니라 여기일 수 있습니다.

### 경로계획·추종 쪽에 부탁드릴 것

가능한 범위에서 아래를 고려해 주시면 방향 정확도가 좋아집니다.
**필수는 아니고, 다른 제약이 우선이면 그쪽을 따라 주세요.**

- 불필요하게 오래 정지하지 않기
- 제자리 회전보다 곡선 주행을 선호하기 (회전 중에는 보정이 멈춤)
- 후진은 되도록 피하기 (방향이 180° 뒤집혀 별도 처리 필요)

회전이 필요한 구간이 길게 이어질 예정이라면 미리 알려주세요. 그 구간에서
방향 오차가 얼마나 쌓일지 미리 계산해서 알려드릴 수 있습니다.

## 5. 신뢰도 신호 — 설계안

```
[  구현 상태: 미작성. 아래는 제안이며 확정 전  ]
```

### 왜 필요한가

대회 규정에 이런 조항이 있습니다.

> 로봇이 통신 두절, 제어 불능, 급가속, 이탈, 추락 위험을 보일 경우
> 심판은 즉시 경기를 중단할 수 있다.

여기서 **제어 불능, 급가속, 이탈은 위치추정이 틀렸을 때 나타나는 증상**입니다.

예를 들어 GPS 가 순간적으로 5 m 튀면, 경로추종기는 "경로에서 5 m 벗어났다"고
판단하고 크게 보정합니다. 밖에서 보면 로봇이 갑자기 방향을 확 트는 것으로
보이고, 이게 급가속이나 이탈로 판정될 수 있습니다.

**위치를 못 믿을 상태라는 걸 아는 건 위치추정 쪽뿐입니다.** 그래서 그 정보를
신호로 내보내려 합니다.

### 규격 (제안)

```
[  토픽명: 위치추정 신뢰도 (미정)  ]
[  메시지 타입: diagnostic_msgs/DiagnosticStatus 또는 std_msgs/UInt8 (미정)  ]
[  발행 주기 (미정)  ]
```

세 단계로 나누는 것을 제안합니다.

| 단계 | 상태 | 뜻 | 권장 동작 |
|---|---|---|---|
| 0 | OK | 정상 | 평소대로 |
| 1 | WARN | 정확도 저하 | **감속**, 큰 보정 자제 |
| 2 | ERROR | 못 믿음 | **정지** |

판단 근거도 함께 실을 예정입니다. 참고용이며 직접 해석하지 않으셔도 됩니다.

| 항목 | 뜻 |
|---|---|
| 방향 불확실성 | 지금 방향을 얼마나 믿을 수 있는가 (도) |
| 위치 불확실성 | 지금 위치를 얼마나 믿을 수 있는가 (m) |
| GPS 위성 수 | 많을수록 좋음 |
| HDOP | GPS 품질 지표. 낮을수록 좋음 |
| 마지막 GPS 후 경과 | 오래되면 위험 |

**단계 판정 기준은 아직 정하지 않았습니다.**

```
[  판정 임계값: 각 단계로 넘어가는 기준 수치 (미정)
   실외 실험에서 실제 분포를 본 뒤 정할 예정  ]
```

### 세 단계로 나눈 이유

정상/비정상 두 단계로 하면 GPS 가 잠깐 흔들릴 때마다 급정지하게 됩니다.
레이싱에서는 기록도 나빠지고, **갑작스러운 정지 자체가 위험**할 수 있습니다.

중간 단계를 두어 "조심해서 계속 간다"는 선택지를 만들었습니다.

### 논의가 필요한 부분

각 단계에서 구체적으로 어떻게 동작할지는 받는 쪽에서 정하시는 게 맞다고
생각합니다.

```
[  WARN 시 동작: 감속 비율 등 (미정 — 주행 담당 결정)  ]

[  ERROR 시 동작: 즉시 정지 / 몇 초 지속 후 정지 (미정 — 주행 담당 결정)  ]

[  복귀 조건: OK 로 돌아왔을 때 바로 재가속할지 여부 (미정 — 주행 담당 결정)  ]
```

**비상정지 자체의 구현은 주행 담당 쪽에 있다고 이해하고 있습니다.**
위치추정 쪽은 판단 근거를 신호로 제공하는 역할입니다. 이 분담이 맞는지
한 번 확인해 주시면 좋겠습니다.

```
[  비상정지 담당 확정 (미정)  ]
```

| 항목 | 상태 | 영향 |
|---|---|---|
| 코스 경계물 종류 | 12월 확인 예정 | 벽이면 라이다 위치추정 추가 가능 |
| 목표 주행 속도 | **협의 필요** | 3 m/s 면 GPS 주기가 병목 |
| A\* 격자를 어떻게 줄지 | **협의 필요** | 아래 참조 |
| 긴급정지 사양 | 확인 예정 | — |

### A\* 에 넣을 격자에 대해

A\* 가 격자를 필요로 하는 건 맞는데, 그 격자를 만드는 방법이 두 가지입니다.

| | 미리 만들어 저장 | 주행 중 매번 새로 |
|---|---|---|
| 만드는 시점 | 경기 전 스캔 | 실시간 |
| 필요한 것 | 정확한 자기 위치 | 지금 라이다에 보이는 것뿐 |
| 동적 장애물 | 반영 안 됨 | 반영됨 |

**실외에서는 두 번째가 유리합니다.** 자기 위치가 GPS 기준 2.4 m 오차라서,
미리 지도를 만들면 장애물도 그만큼 어긋난 자리에 기록됩니다. 실내에서는
0.24 m 였기 때문에 문제가 안 됐지만 실외는 다릅니다.

경기 전 스캔 기회가 있다고 들었는데, 그때는 **점군 지도 대신 코스를 따라가는
GPS 웨이포인트 목록을 뽑는 방식**을 제안드립니다. 스캔할 때 지나간 경로가 곧
가야 할 경로이니, 그걸 저장해서 따라가면 됩니다.

**다만 전역 지도가 필요하다고 보신 이유가 따로 있다면 알려주세요.**
코스에 대해 제가 모르는 조건(막다른 길, 코스가 겹치는 구간 등)이 있으면
판단이 달라집니다.

### 경계물

코스 양옆에 세워질 것이 벽인지 휀스인지 콘인지 아직 정해지지 않았습니다.

| 경계물 | 라이다에 어떻게 보이는가 | 결과 |
|---|---|---|
| 벽 | 연속된 면 | 라이다 위치추정을 되살릴 수 있음 |
| 휀스 | 성긴 반사 | 부분적. 검증 필요 |
| 콘 | 흩어진 점 몇 개 | 현재 계획 유지 (GPS 의존) |

**지금은 가장 불리한 콘을 가정하고 설계합니다.** 벽으로 확정되면 그때 라이다를
추가하는 쪽이, 반대 경우보다 훨씬 쉽기 때문입니다.

### 속도에 대해

현재 측정 데이터는 0.82 m/s 기준입니다. 레이싱이니 더 빠르게 가실 것 같은데,
**목표 속도를 알려주시면** 그에 맞춰 설계를 조정할 수 있습니다.

GPS 는 1 초에 한 번만 갱신됩니다. 3 m/s 로 달리면 갱신 사이에 3 m 를 이동하고,
그동안은 추측으로 위치를 메웁니다. 속도가 빠를수록 이 구간의 오차가 커집니다.

```
[  목표 주행 속도 (미정 — 주행 담당과 협의)  ]
```

## 부록 — 용어

**IMU** — 관성측정장치. 가속도계와 자이로스코프가 들어 있습니다. 로봇이 얼마나
빨리 도는지, 어느 쪽으로 기울었는지를 잽니다.

**자이로스코프** — 회전 속도를 재는 센서. 각도를 직접 재는 게 아니라 회전
속도를 재기 때문에, 각도를 얻으려면 계속 더해야 합니다. 그래서 오차도 같이
쌓입니다.

**LIO** — Lidar-Inertial Odometry. 라이다와 IMU 를 합쳐 위치를 추정하는 방법.

**오도메트리(odometry)** — 얼마나 움직였는지를 누적해서 위치를 알아내는 방법.
자동차 주행거리계와 비슷한 개념입니다. 출발점 기준 상대 위치라 시간이 지나면
오차가 쌓입니다.

**EKF** — 확장 칼먼 필터. 여러 센서 값을 합쳐 가장 그럴듯한 값을 추정하는
알고리즘. 각 센서가 얼마나 믿을 만한지를 함께 계산합니다.

**공분산(covariance)** — 추정값이 얼마나 불확실한지를 나타내는 수치. 클수록
덜 믿을 만합니다.

**HDOP** — GPS 위성 배치가 얼마나 좋은지를 나타내는 값. 낮을수록 좋고, 1 이하면
양호합니다. 운동장 측정에서는 평균 0.82 였습니다.

**TF** — ROS 의 좌표 변환 시스템. 프레임 사이 관계를 관리해 주어서, 한 좌표계의
값을 다른 좌표계로 바꿀 때 직접 계산하지 않아도 됩니다.

**웨이포인트** — 경로 위에 찍어둔 목표 지점들.
