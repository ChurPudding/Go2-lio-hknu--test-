# 실외 자율주행 — 위치추정 인터페이스

작성 2026-08-02. 담당: 위치추정·지도·GPS

이 문서는 **실외에서 위치추정 쪽이 무엇을 내보내고, 받는 쪽이 그것을 어떻게
쓰면 되는지**를 정리한 것입니다. 경로계획·추종을 맡은 쪽에서 주로 보시면 되고,
장애물 인식 쪽에서도 5장(신뢰도 신호)은 관련이 있습니다.

배경을 모르셔도 읽을 수 있게 썼습니다. 처음 보는 용어는 부록에 정리해 두었으니
필요할 때 참고해 주세요.

실내 구조는 `docs/INTERFACE_indoor.md` 에 따로 있습니다.

> **읽는 방법**
> 대괄호 `[   ]` 로 표시된 곳은 **아직 정해지지 않았거나 만들지 않은 것**입니다.
> 괄호 안에 무엇을 채워야 하는지 적어 두었습니다.
> 3장의 "구현됨" 표시가 있는 항목만 지금 실제로 존재합니다.

## 1. 실외는 실내와 구조가 다릅니다

### 실내에서 하던 방식

실내에서는 라이다로 주변 벽과 기둥을 보면서 위치를 알아냈습니다.
이걸 **LIO**(라이다-관성 오도메트리)라고 합니다. 복도에서 26 m 를 돌아
제자리로 왔을 때 오차가 0.24 m 였으니 상당히 정확했습니다.

원리는 간단합니다. 벽이 옆에 있으면 "내가 벽에서 1.2 m 떨어져 있다"를 알 수
있고, 앞뒤로 움직이면 벽의 무늬가 흘러가는 속도로 얼마나 갔는지 알 수 있습니다.
**주변에 특징이 있어야 위치를 알 수 있다**는 게 핵심입니다.

### 실외에서는 그게 안 됩니다

7/31 에 운동장에서 356 m 를 주행하며 측정한 결과입니다.

| 방법 | 최종 수평 오차 |
|---|---|
| GPS | 2.4 m |
| LIO (FAST-LIO) | 110 m |
| LIO (Point-LIO) | 26,695 m |
| IMU 단독 | 84,829 m |

LIO 가 완전히 무너졌습니다. 이유는 **점군의 96~99% 가 지면**이었기 때문입니다.
운동장은 사방이 트여 있어서 라이다에 잡히는 게 바닥밖에 없습니다.

평평한 바닥만 보고 있으면 "내가 바닥 위 0.4 m 에 있다"는 알 수 있어도,
**앞으로 갔는지 옆으로 갔는지, 어느 쪽을 보고 있는지는 알 수 없습니다.**
바닥은 어디를 봐도 똑같이 생겼기 때문입니다.

교정으로 해결되지 않는다는 것도 확인했습니다. 최적으로 맞춘 뒤에도 잔차가
89.6 m 였고, 궤적 모양 자체가 달랐습니다.

### 그래서 실외에서는 GPS 를 씁니다

| 역할 | 담당 센서 |
|---|---|
| 지금 어디에 있는가 | GPS |
| 어느 쪽을 보고 있는가 | GPS + IMU (4장 참조) |
| 눈앞에 뭐가 있는가 | 라이다 (장애물 인식 담당) |

**실외에서는 점군 지도를 만들지 않습니다.** GPS 웨이포인트 목록이 곧 경로이고,
장애물은 그때그때 피합니다.

## 2. 좌표계 약속

여러 사람이 만든 코드가 붙으므로 좌표 규약을 먼저 맞춰야 합니다.
ROS 표준(REP-103)을 따릅니다.

**프레임 세 개**

| 프레임 | 뜻 |
|---|---|
| `map` | 출발 지점을 원점으로 하는 고정 좌표계. GPS 로 보정되므로 **튈 수 있음** |
| `odom` | 부드럽게 이어지는 좌표계. 튀지 않지만 시간이 지나면 조금씩 어긋남 |
| `base` | 로봇 몸통 (실내와 동일. URDF 의 루트 링크) |

**둘을 나누는 이유**가 있습니다. GPS 는 정확하지만 1 초에 한 번 갱신되면서
값이 조금씩 튑니다. 이걸 그대로 쓰면 로봇 위치가 순간이동하는 것처럼 보이고,
경로추종기가 놀라서 급격한 명령을 냅니다.

그래서 **`odom` 은 부드럽게, `map` 은 정확하게** 두 개를 유지합니다.

- **속도 제어처럼 부드러움이 중요한 계산** → `odom` 프레임 사용
- **웨이포인트까지 얼마나 남았는지 같은 계산** → `map` 프레임 사용

**축 방향**

- x = 동쪽, y = 북쪽, z = 위
- 각도는 **동쪽이 0°**, 반시계 방향이 +
- 단위는 미터, 초, 라디안

북쪽이 0° 가 아니라는 점에 주의해 주세요. 나침반과 다릅니다.

## 3. 토픽

### 3.1 지금 존재하는 것

아래는 실제로 동작을 확인한 것들입니다. 다만 **주행 담당 쪽에서 직접 쓰실
것은 아닙니다.** 3.2 의 출력이 나오면 그것을 쓰시면 됩니다.

| 토픽 | 타입 | 주기 | 비고 |
|---|---|---|---|
| `/gnss` | `std_msgs/String` | 1 Hz | Go2 원본. JSON 문자열 |
| `/gps/fix` | `sensor_msgs/NavSatFix` | 1 Hz | `tools/gnss_bridge.py` 출력. **검증 완료** |
| `/gps/path` | `nav_msgs/Path` | 1 Hz | `tools/gnss_path.py` 출력. RViz 확인용 |
| `/lowstate` | `unitree_go/LowState` | 500 Hz | Go2 원본. IMU 포함 |
| `/sportmodestate` | `unitree_go/SportModeState` | 약 300 Hz | Go2 원본. 속도·발 위치 |
| `/utlidar/cloud` | `sensor_msgs/PointCloud2` | 15 Hz | 원시 점군 |
| `/utlidar/robot_odom` | `nav_msgs/Odometry` | 150 Hz | Go2 내장 다리 오도메트리 |

**주의 — `/utlidar/robot_odom` 은 실외에서 위치로 쓸 수 없습니다.**
356 m 주행에서 수평 오차 RMS 10.2 m, 최대 20.0 m 였습니다.

### 3.2 만들 예정인 것 — 아직 없음

아래는 **아직 구현되지 않았습니다.** 이름도 확정 전이므로 비워 둡니다.
정해지는 대로 이 문서를 갱신하겠습니다.

**주 위치 출력**

```
[  토픽명: map 프레임 기준 로봇 위치·자세·속도 (미정)  ]
  타입   nav_msgs/Odometry
  프레임 map
  주기   [  발행 주기: EKF 설정에 따라 결정 (미정)  ]
```

경로추종에 쓰실 **주 입력**이 될 예정입니다. `pose.covariance` 에 불확실성이
함께 들어갑니다.

**부드러운 위치 출력**

```
[  토픽명: odom 프레임 기준 위치 (미정)  ]
  타입   nav_msgs/Odometry
  프레임 odom
  주기   [  발행 주기 (미정)  ]
```

GPS 보정이 들어가지 않아 **튀지 않습니다.** 대신 시간이 지나면 실제 위치와
어긋납니다. 속도 제어처럼 짧은 시간 안의 변화만 보는 계산에 쓰시면 됩니다.

**신뢰도 신호** — 5장 참조

**TF**

```
[  TF 발행 계획: map → odom → base 를 어느 노드가 낼지 (미정)  ]
```

### 3.3 상태 감시 도구 — 파일은 있으나 실외 연동 전

| 파일 | 내용 | 발행 토픽 |
|---|---|---|
| `tools/lio_health.py` | 정지 중 표류·속도 불일치·z 급변 감시 | `[  토픽명 확인 필요  ]` |
| `tools/proximity_guard.py` | 원시 점군 기반 근접 경고. LIO 비의존 | `[  토픽명 확인 필요  ]` |

실내용으로 만든 것이라 실외 조건에 맞게 손봐야 합니다.

## 4. 방향(heading)에 관한 주의사항

이 부분이 실외에서 가장 까다로운 지점이라 따로 설명드립니다.

### Go2 는 나침반이 없습니다

조사 결과 Go2 의 방향값은 **자이로스코프를 적분해서 만든 값**이었습니다.
자이로는 "얼마나 빨리 돌고 있는가"를 재는 센서라, 이걸 계속 더하면 "지금까지
얼마나 돌았는가"가 나옵니다.

문제가 두 가지입니다.

**첫째, 기준이 없습니다.** 전원을 켠 순간의 방향이 0° 입니다. 북쪽이 아닙니다.
로봇을 껐다 켜면 기준이 바뀝니다.

**둘째, 시간이 지나면 어긋납니다.** 측정해 보니 **분당 2~5°** 씩 틀어졌습니다.
5 분이면 10~25° 입니다. 코스 폭이 3 m 라면 금방 벗어나는 크기입니다.

게다가 이 값이 같은 날 안에서도 세 배까지 변했습니다. 미리 보정값을 정해두는
방식으로는 해결되지 않습니다.

### GPS 로 계속 고쳐 나갈 예정입니다

로봇이 앞으로 걸어가면, GPS 위치가 이동한 방향이 곧 로봇이 향한 방향입니다.
이걸로 자이로의 어긋남을 계속 되돌립니다.

오프라인 분석에서 5 m 를 이동한 두 지점으로 계산했을 때 **오차 약 8°** 였습니다.
개별 값은 부정확하지만 계속 들어오므로 평균 내면 훨씬 정확해집니다.

```
[  구현 상태: 오프라인 분석만 완료. 실시간 노드 미작성  ]
```

**그런데 이 방법에는 사각지대가 있습니다.**

| 상황 | 방향 보정 |
|---|---|
| 직진 중 | 잘 됨 |
| 정지 중 | **불가** — 이동이 없으니 방향을 알 수 없음 |
| 제자리 회전 중 | **불가** |
| 옆으로 걸을 때 | 부정확 |

즉 **오래 멈춰 있거나 제자리에서 많이 돌면 방향 정확도가 나빠집니다.**
30 초 정지에 1~2.5° 정도입니다.

### 경로계획·추종 쪽에 부탁드릴 것

가능한 범위에서 아래를 고려해 주시면 방향 정확도가 좋아집니다.
**필수는 아니고, 다른 제약이 우선이면 그쪽을 따라 주세요.**

- 불필요하게 오래 정지하지 않기
- 제자리 회전보다 곡선 주행을 선호하기 (회전 중에는 보정이 멈춤)
- 후진은 되도록 피하기 (방향이 180° 뒤집혀 별도 처리 필요)

회전이 필요한 구간이 길게 이어질 예정이라면 미리 알려주세요. 그 구간에서
방향 오차가 얼마나 쌓일지 미리 계산해서 알려드릴 수 있습니다.

## 5. 신뢰도 신호 — 설계안

```
[  구현 상태: 미작성. 아래는 제안이며 확정 전  ]
```

### 왜 필요한가

대회 규정에 이런 조항이 있습니다.

> 로봇이 통신 두절, 제어 불능, 급가속, 이탈, 추락 위험을 보일 경우
> 심판은 즉시 경기를 중단할 수 있다.

여기서 **제어 불능, 급가속, 이탈은 위치추정이 틀렸을 때 나타나는 증상**입니다.

예를 들어 GPS 가 순간적으로 5 m 튀면, 경로추종기는 "경로에서 5 m 벗어났다"고
판단하고 크게 보정합니다. 밖에서 보면 로봇이 갑자기 방향을 확 트는 것으로
보이고, 이게 급가속이나 이탈로 판정될 수 있습니다.

**위치를 못 믿을 상태라는 걸 아는 건 위치추정 쪽뿐입니다.** 그래서 그 정보를
신호로 내보내려 합니다.

### 규격 (제안)

```
[  토픽명: 위치추정 신뢰도 (미정)  ]
[  메시지 타입: diagnostic_msgs/DiagnosticStatus 또는 std_msgs/UInt8 (미정)  ]
[  발행 주기 (미정)  ]
```

세 단계로 나누는 것을 제안합니다.

| 단계 | 상태 | 뜻 | 권장 동작 |
|---|---|---|---|
| 0 | OK | 정상 | 평소대로 |
| 1 | WARN | 정확도 저하 | **감속**, 큰 보정 자제 |
| 2 | ERROR | 못 믿음 | **정지** |

판단 근거도 함께 실을 예정입니다. 참고용이며 직접 해석하지 않으셔도 됩니다.

| 항목 | 뜻 |
|---|---|
| 방향 불확실성 | 지금 방향을 얼마나 믿을 수 있는가 (도) |
| 위치 불확실성 | 지금 위치를 얼마나 믿을 수 있는가 (m) |
| GPS 위성 수 | 많을수록 좋음 |
| HDOP | GPS 품질 지표. 낮을수록 좋음 |
| 마지막 GPS 후 경과 | 오래되면 위험 |

**단계 판정 기준은 아직 정하지 않았습니다.**

```
[  판정 임계값: 각 단계로 넘어가는 기준 수치 (미정)
   실외 실험에서 실제 분포를 본 뒤 정할 예정  ]
```

### 세 단계로 나눈 이유

정상/비정상 두 단계로 하면 GPS 가 잠깐 흔들릴 때마다 급정지하게 됩니다.
레이싱에서는 기록도 나빠지고, **갑작스러운 정지 자체가 위험**할 수 있습니다.

중간 단계를 두어 "조심해서 계속 간다"는 선택지를 만들었습니다.

### 논의가 필요한 부분

각 단계에서 구체적으로 어떻게 동작할지는 받는 쪽에서 정하시는 게 맞다고
생각합니다.

```
[  WARN 시 동작: 감속 비율 등 (미정 — 주행 담당 결정)  ]

[  ERROR 시 동작: 즉시 정지 / 몇 초 지속 후 정지 (미정 — 주행 담당 결정)  ]

[  복귀 조건: OK 로 돌아왔을 때 바로 재가속할지 여부 (미정 — 주행 담당 결정)  ]
```

**비상정지 자체의 구현은 주행 담당 쪽에 있다고 이해하고 있습니다.**
위치추정 쪽은 판단 근거를 신호로 제공하는 역할입니다. 이 분담이 맞는지
한 번 확인해 주시면 좋겠습니다.

```
[  비상정지 담당 확정 (미정)  ]
```

## 6. 아직 정해지지 않은 것

| 항목 | 상태 | 영향 |
|---|---|---|
| 코스 경계물 종류 | 12월 확인 예정 | 벽이면 라이다 위치추정 추가 가능 |
| 목표 주행 속도 | **협의 필요** | 3 m/s 면 GPS 주기가 병목 |
| 긴급정지 사양 | 확인 예정 | — |

### 경계물

코스 양옆에 세워질 것이 벽인지 휀스인지 콘인지 아직 정해지지 않았습니다.

| 경계물 | 라이다에 어떻게 보이는가 | 결과 |
|---|---|---|
| 벽 | 연속된 면 | 라이다 위치추정을 되살릴 수 있음 |
| 휀스 | 성긴 반사 | 부분적. 검증 필요 |
| 콘 | 흩어진 점 몇 개 | 현재 계획 유지 (GPS 의존) |

**지금은 가장 불리한 콘을 가정하고 설계합니다.** 벽으로 확정되면 그때 라이다를
추가하는 쪽이, 반대 경우보다 훨씬 쉽기 때문입니다.

### 속도에 대해

현재 측정 데이터는 0.82 m/s 기준입니다. 레이싱이니 더 빠르게 가실 것 같은데,
**목표 속도를 알려주시면** 그에 맞춰 설계를 조정할 수 있습니다.

GPS 는 1 초에 한 번만 갱신됩니다. 3 m/s 로 달리면 갱신 사이에 3 m 를 이동하고,
그동안은 추측으로 위치를 메웁니다. 속도가 빠를수록 이 구간의 오차가 커집니다.

```
[  목표 주행 속도 (미정 — 주행 담당과 협의)  ]
```

## 부록 — 용어

**IMU** — 관성측정장치. 가속도계와 자이로스코프가 들어 있습니다. 로봇이 얼마나
빨리 도는지, 어느 쪽으로 기울었는지를 잽니다.

**자이로스코프** — 회전 속도를 재는 센서. 각도를 직접 재는 게 아니라 회전
속도를 재기 때문에, 각도를 얻으려면 계속 더해야 합니다. 그래서 오차도 같이
쌓입니다.

**LIO** — Lidar-Inertial Odometry. 라이다와 IMU 를 합쳐 위치를 추정하는 방법.

**오도메트리(odometry)** — 얼마나 움직였는지를 누적해서 위치를 알아내는 방법.
자동차 주행거리계와 비슷한 개념입니다. 출발점 기준 상대 위치라 시간이 지나면
오차가 쌓입니다.

**EKF** — 확장 칼먼 필터. 여러 센서 값을 합쳐 가장 그럴듯한 값을 추정하는
알고리즘. 각 센서가 얼마나 믿을 만한지를 함께 계산합니다.

**공분산(covariance)** — 추정값이 얼마나 불확실한지를 나타내는 수치. 클수록
덜 믿을 만합니다.

**HDOP** — GPS 위성 배치가 얼마나 좋은지를 나타내는 값. 낮을수록 좋고, 1 이하면
양호합니다. 운동장 측정에서는 평균 0.82 였습니다.

**TF** — ROS 의 좌표 변환 시스템. 프레임 사이 관계를 관리해 주어서, 한 좌표계의
값을 다른 좌표계로 바꿀 때 직접 계산하지 않아도 됩니다.

**웨이포인트** — 경로 위에 찍어둔 목표 지점들.
