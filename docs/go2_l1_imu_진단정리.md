# Go2 L1 LIO 회전 발산 문제 — 원인 규명 및 해결

작성일 2026-07-29 · 분석 대상 `go2_run_full` (110초, 135,680 메시지, 실내 평지)

---

## 1. 문제

Point-LIO를 Go2에 올렸을 때 **직진 구간은 정상인데 회전 구간에서 궤적이 아래로 처지며 S자로 휘는** 현상이 지속됐다. `gravity_align` true/false, `gravity` 벡터 변경 등을 시도했으나 모두 동일한 결과였다.

오프라인 재현 결과 실제로는 처짐이 아니라 **완전 발산**이었다.

| | before (`acc_norm` 9.81) | after (`acc_norm` 10.41) |
|---|---|---|
| 발산 시작 | t = 7.79 s | t = 7.79 s |
| 최종 z | −15,984 m | −15,338 m |
| 수평 총거리 | 24,185 m | 16,976 m |

발산 시점 7.79초는 **첫 회전 구간(R0, 6.65~7.94 s) 한가운데**다. 정지 상태인 6.6초까지는 오차 1~7 cm로 멀쩡하다가 로봇이 처음 제자리 회전을 시작하는 순간 터진다.

---

## 2. 기준선 검증 — `/utlidar/robot_odom`

정량 평가를 하려면 믿을 수 있는 참값이 먼저 필요했다.

| 항목 | 값 |
|---|---|
| z 범위 | 0.290 ~ 0.322 m |
| z 표준편차 | 5.1 mm |
| z peak-to-peak | 31.8 mm (110초 전체) |
| 시작 z → 끝 z | 0.3049 → 0.3031 (**차이 1.8 mm**) |
| roll / pitch 평균 | −0.76° / +0.44° (중력 정렬 프레임) |
| 총 경로 / 루프 클로저 | 32.85 m / 0.56 m (1.7%) |
| 누적 yaw | 순 −362.7°, 절대값 합 2281° |

**z만 특별히 깨끗한 이유:** x·y·yaw는 다리 운동학의 *적분*이라 시간에 비례해 드리프트하지만, **z는 적분이 아니다.** 발이 지면에 닿아 있을 때 관절각으로부터 몸통 높이를 직접 계산하므로 매 스텝마다 지면이 z를 재고정한다.

→ **z 처짐 판정은 `robot_odom` z를 정답으로 사용 (허용 ±20 mm), 수평 정확도는 루프 클로저로 판정.**

회전 구간은 자이로를 실측 중력축에 투영해 16개를 식별했다. 주요 구간: R2(15.7~18.5 s, +153.8°), R3(27.7~30.5 s, +172.0°), R6(38.2~40.7 s, +170.1°), R8(46.5~49.3 s, −159.7°), R9(51.3~53.7 s, −167.0°), R14(85.5~89.2 s, −186.4°).

## 3. 원인 규명

### 3.1 좌표계 세 개가 서로 다르다

정지 상태에서 중력(연직) 방향을 각 좌표계에서 관측한 값:

| 좌표계 | 관측된 up 벡터 | 자기 +z에서 |
|---|---|---|
| LiDAR 클라우드 (`/utlidar/cloud`) | (+0.154, −0.178, −0.972) | 166.4° (**+z가 아래**) |
| L1 **자이로** (`/utlidar/imu`) | (+0.149, −0.211, −0.966) | — |
| L1 **가속도계** (`/utlidar/imu`) | (+0.342, −0.000, +0.940) | 20.0° |
| 본체 IMU (`/lowstate`) | (−0.009, −0.026, +1.000) | 1.6° |

- LiDAR ↔ 자이로: **1.87° 일치** ✓
- LiDAR ↔ 가속도계: **149.4° 불일치** ✗

지면 평면 추정은 견고하다 — 누적 스캔에서 5×6 m에 걸쳐 5만 점(38%)이 평면에 들어맞고, 두 번째로 큰 평면이 87.9°로 직교하는 벽이다.

LiDAR 기울기 13.6°는 URDF `radar` 링크의 164.9° pitch와 일치하며, 자이로가 클라우드 좌표계와 평행하다는 것은 Unitree 공식 스펙(*"The IMU frame's axes are aligned and parallel to the point cloud coordinate system"*)과 부합한다.

**→ `extrinsic_R: identity`는 원래 옳았다. 문제는 가속도계 하나다.**

### 3.2 결정적 검증 — 실제 가속도와의 상관

IMU 가속도를 `robot_odom` 자세로 월드 프레임에 회전시킨 뒤, odom 위치의 2차 미분과 상관을 냈다.

| 가정 | ax 상관 | ay 상관 | az 평균 |
|---|---|---|---|
| 가속도계 = LiDAR/자이로 프레임 | −0.187 | −0.130 | −8.967 |
| 위 + 부호 반전 | +0.187 | +0.130 | +8.967 |
| 가속도계 자기 up 기준 20° 틀 | −0.036 | +0.168 | +10.394 |
| **본체 IMU (`/lowstate`)** | **+0.833** | **+0.787** | **+9.455** |

**어떤 좌표 변환을 넣어도 L1 가속도계는 실제 로봇 가속도를 따라가지 못한다(≤0.19).** 회전으로 고칠 수 있는 문제가 아니라 데이터 자체가 못 쓰는 상태다. 본체 IMU는 0.83/0.79로 확연히 다르다.

### 3.3 왜 회전에서만 터지는가

중력 방향이 149° 틀린 채로 초기화되면, 자세가 변하지 않는 직진에서는 그 오차가 상수 가속도 바이어스로 흡수된다. 하지만 **회전이 시작되면 바이어스와 실제 오차 방향이 어긋나면서 즉시 발산한다.** 이 데이터는 누적 회전 2281°에 최대 165°/s로 회전 비중이 극단적이라 증상이 특히 크게 나타났다.

`gravity_align` true/false가 같은 결과였던 것도 설명된다 — 두 설정 모두 월드축의 *방향*만 다루고, 깨진 가속도계 데이터 자체는 건드리지 않는다.

### 3.4 부수적으로 확인된 사실

| 항목 | 값 |
|---|---|
| L1 가속도계 정지 \|a\| | 10.437 m/s² (**+6.4%**) |
| 본체 가속도계 정지 \|a\| | 9.465 m/s² (**−3.5%**) |
| L1 자이로 바이어스 | ≤ 0.059 °/s (양호) |
| 본체 자이로 110초 적분 오차 | −372.0° vs 참값 −362.7° (**2.6%**) |
| 최대 각속도 | 2.89 rad/s (`satu_gyro` 35의 8%, 포화 없음) |
| IMU 레이트 | 249.7 Hz (`imu_time_inte: 0.004` 정확) |
| 클라우드 | 15.4 Hz, 4,143점/스캔, `time`·`ring` 필드 정상 |

L1 가속도계의 +6.4% 스케일 오차는 실측으로 확정되지만 **발산의 원인은 아니었다.**

### 3.5 외부 파라미터 정리 (회전 + 평행이동)

**회전** `R_BL` (LiDAR → base_link): 4절 참조. 자이로 Kabsch, 설명력 98.0%, yaw 성분 −127.9° ± 0.5°.

**평행이동** `r` (base_link 원점 → LiDAR 원점, base_link 프레임 표현):

`p_L^{ci} = R_z(\alpha)\,(p_B^{odom} + R_B^{odom} r) + d` 형태로, 8초 창 13개에 창별 정렬(α, d)을 따로 두고 `r`을 공유해 최소자승으로 추정.

| 성분 | 값 | 근거 |
|---|---|---|
| x | **+0.322 m** | 창 분할 최소자승. 잔차 0.238 → 0.143 m (**40% 개선**) |
| y | **+0.005 m** | 같음. 방향 +0.9° = 거의 정확히 정면 |
| z | **+0.050 m** (추정) | **관측 불가.** 몸통 roll/pitch 변화 부족으로 평행이동 항과 상쇄됨. 지면까지 거리 0.355~0.364 m 와 몸통 높이 0.308 m 에서 역산 |

Go2 머리에 L1이 얹힌 물리 구조와 일치한다. x·y는 신뢰할 수 있고, z는 정밀도가 필요하면 실측할 것. 평지 주행에서는 z 수 cm 오차가 문제되지 않는다.

**함의:** `/aft_mapped_to_init`은 **LiDAR 원점**의 궤적이다. 로봇 몸통 위치를 얻으려면

```
p_base(map) = p_lidar(map) − R_ML · R_LB · r
```

보정 없이 쓰면 **제자리 회전만으로도 반지름 0.32 m 원호**가 그려진다. 구현은 `robot_pose.py`.

**검증법:** 로봇을 제자리에서 한 바퀴 돌린다. `/aft_mapped_to_init`의 x·y는 반지름 0.32 m 원, `/robot_pose`의 x·y는 제자리, heading은 360° 증가(반시계 +).

## 4. 해결책 — 두 IMU의 멀쩡한 부분 합치기

| 신호 | 출처 | 근거 |
|---|---|---|
| 자이로 | `/utlidar/imu` 그대로 | 이미 LiDAR 프레임 (1.87° 일치) |
| 가속도계 | `/lowstate` 본체 → LiDAR 프레임으로 회전 | 실제 가속도와 상관 0.83 |

IMU 프레임 = LiDAR 프레임이 되므로 **`extrinsic_R`은 단위행렬 그대로** 둘 수 있다.

**본체 → LiDAR 회전.** 두 자이로가 같은 강체의 각속도를 서로 다른 프레임에서 관측하므로, 벡터쌍을 Kabsch 정렬하면 회전이 3자유도 전부 유일하게 결정된다. 두 IMU의 내부 필터 대역이 달라 위상이 어긋나므로 **양쪽을 2 Hz 저역통과로 맞춘 뒤** 정렬한다 (설명력 87.7% → **98.0%**). 시간지연 −6 ms 보정.

```
R_LB = [ +0.523029, -0.838576, +0.152420,
         -0.810712, -0.544668, -0.214668,
         +0.263034, -0.011292, -0.964721 ]
```

검증: `R_LB @ (본체 up)` 이 LiDAR up과 1.24° 일치. 정지 시 예상 가속도 (1.658, −1.895, −9.478).

가속도는 9.807/9.465 = 1.0361 배로 스케일 보정한다.

### 구현

`l1_imu_fix.py` — `/utlidar/imu`와 `/lowstate`를 구독해 `/l1_imu_fixed`(250 Hz, RELIABLE QoS) 발행.

### 설정 변경

```yaml
common:
    imu_topic: "/l1_imu_fixed"           # was /utlidar/imu
mapping:
    acc_norm: 9.81                       # 노드에서 정규화하므로 표준값
    gravity_align: true                  # was false
    gravity:      [0.0, 0.0, -9.810]
    gravity_init: [0.0, 0.0, -9.810]
    extrinsic_R: [1,0,0, 0,1,0, 0,0,1]   # 변경 없음
    extrinsic_T: [0.007698, 0.014655, -0.00667]
```

### 사전 검증 포인트

정지 구간에서 `/l1_imu_fixed`의 `linear_acceleration`이 **(+1.5, −1.7, −9.5)** 근처여야 한다.
실측: **(1.56, −1.81, −9.51)** ✓

## 6. 남은 과제

### 6.1 수평 경로가 44% 길다 (46.9 m vs 32.5 m)

궤적 형상은 맞으나 잔떨림이 크다. 6.2가 해결되면서 원인 후보가 하나로 좁혀졌다.

- ~~`R_LB`의 미확정 yaw 성분~~ → **0.3° 이내 정확함이 확인되어 원인에서 제외**
- **출력 레이트 8.5 kHz** — `publish_odometry_without_downsample: true`로 포인트 단위 출력이라 잡음이 그대로 실림. `false`로 바꿔 확인할 것. **남은 유일한 후보.**

### 6.2 `R_LB`의 yaw 성분 — 해결됨

초기에는 세 방법이 갈렸다.

| 방법 | 결과 | 판정 |
|---|---|---|
| 자이로 Kabsch (대역 미조정) | −128.0° | 설명력 87.7% |
| 벽 거리 회귀 | −2.5° | 비용함수 평탄, 판별력 없음 → **폐기** |
| 지도 선명도 | −125° / +60° / +130° (창별) | 불일치 → **폐기** |

원인은 **두 IMU의 내부 필터 대역폭 차이로 인한 위상 어긋남**이었다. 양쪽을 같은 저역통과에 통과시킨 뒤 정렬하니 해소됐다.

| 저역통과 | 최적 지연 | 설명력 | 함의 θ |
|---|---|---|---|
| 2 Hz | −6 ms | **98.0%** | −128.10° |
| 5 Hz | −7 ms | 97.1% | −127.70° |
| 10 Hz | −8 ms | 96.0% | −127.70° |
| 20 Hz | −8 ms | 94.0% | −128.00° |
| 40 Hz | −8 ms | 90.7% | −128.10° |

독립된 시간 창 7개(각 13.5초)에서도 −126.9° ~ −128.4°로 일치하며, 각 창 설명력 96.9~97.9%.

**θ = −127.9° ± 0.5° 확정.** 정밀화된 `R_LB`은 4절 참조. 기존 값과의 차이는 0.294°로, 이미 얻은 검증 결과(5절)는 그대로 유효하다.

**교훈:** 서로 다른 IMU를 비교·정렬할 때는 **대역폭을 먼저 맞춰야 한다.** 위상차만으로 설명력이 10%p 넘게 깎이고, 그 탓에 옳은 추정을 의심하게 된다.

LI-Init(`hku-mars/LiDAR_IMU_Init`)을 통한 독립 교차검증은 여전히 해볼 가치가 있으나, 더 이상 필수는 아니다.

### 6.3 기타

- **`/body_imu` 단독 사용도 이제 선택지다.** θ가 확정되어 `extrinsic_R`에 `R_BL`을 직접 넣을 수 있다. 자이로·가속도 모두 본체 것을 쓰면 500 Hz로 대역이 넓어지고, 110초 적분 오차 2.6%로 검증된 자이로를 쓰게 된다. 하이브리드와 어느 쪽이 나은지는 실험으로 비교할 것 — 세 알고리즘 비교의 변수로 넣을 만하다
- `imu_meas_acc_cov: 0.1`은 본체 IMU 노이즈 특성에 맞춰 재튜닝 여지 있음
- `satu_acc: 30.0` — z축에서 27,504개 중 18개(0.065%) 초과, 영향 미미
- FAST-LIO도 동일한 `/utlidar/imu`를 사용 중 → **같은 문제를 안고 있을 가능성이 높음.** `/l1_imu_fixed`로 교체해 재평가 필요
- yaml 주석 정정: "roll~110/pitch~18"은 orientation 필드에서 온 잘못된 값. 실제 가속도계 프레임 기울기는 pitch +20.0°, roll +0.02°

## 7. 기존 비교 실험의 유효 범위

깨진 IMU로 수행한 FAST-LIO ↔ Point-LIO 비교를 어디까지 쓸 수 있는지 정리한다.

**데이터의 정당성은 문제가 아니다.** `/utlidar/imu`는 Unitree 펌웨어의 실제 출력이고 가공하지 않았다. 그 결함은 실제 하드웨어/펌웨어 결함이므로, 주입 결함(고장 *모델*)보다 오히려 증거 가치가 높다.

### 유효한 주장 — 실패 방식 (정성적·이진적)

| | 149° 오정렬 IMU 하에서의 거동 |
|---|---|
| Point-LIO | 오류 없이 계속 동작하며 −16 km 궤적을 출력 (**fail-silent**) |
| FAST-LIO | "No Effective Points" 에러로 실패를 명시 (**fail-loud**) |

구조적으로 설명된다. FAST-LIO는 스캔 단위로 유효 대응점 수를 검사해 임계 미달 시 에러를 내고, Point-LIO는 포인트 단위로 처리하며 대응점이 부족해도 IMU 예측으로 진행한다.

자율주행 스택에서는 **fail-loud가 fail-silent보다 안전하다.** 조용히 틀린 위치를 내놓는 것이 멈추는 것보다 위험하다. 이 관찰은 근거가 있고 보고 가능하다.

부수적으로, 이전에 겪은 FAST-LIO의 "No Effective Points 에러가 움직일 때만 발생" 현상도 이것으로 설명된다. 중력 방향이 틀리면 IMU 예측 자세가 무너지고, 그 자세로 변환한 스캔이 지도와 겹치지 않아 유효 대응점이 0이 된다. 정지 중에는 예측할 것이 없어 드러나지 않는다.

### 무효한 주장 — 오차 크기 (정량적)

- 드리프트 비교, RMSE 비교, "어느 쪽이 더 정확한가"
- **이유 1 — 바닥 효과.** 두 알고리즘 모두 완전 실패했다. −16 km와 "에러 종료" 사이에는 순서를 매길 척도가 없다. 측정 범위를 벗어난 것이다
- **이유 2 — 결함 조건이 단일.** 149° 오정렬 + 6.4% 스케일 오차가 동시에 걸린 한 조건, 한 데이터셋. 차이가 나도 기울기 탓인지 크기 탓인지 환경 탓인지 분리할 수 없다
- **이유 3 — 순위 역전 가능성.** 정상 조건에서 정확한 알고리즘은 통상 IMU를 더 강하게 신뢰하는 쪽이며, 그럴수록 IMU가 망가지면 더 크게 무너진다. 강건성과 정확도는 자주 상충한다

### 강건성을 정식으로 주장하려면 — 결함 주입

지금 있는 것은 (149°, 완전실패) **한 점**이다. "몇 도까지 견디는가"에 답할 수 없다.

`/l1_imu_fixed`라는 정상 기준선을 확보했으므로, 브리지 노드에 파라미터 두 개를 추가해 스윕한다.

- `fault_tilt_deg` — 가속도 벡터를 수평축 둘레로 0 / 5 / 10 / 20 / 45 / 90 / 149° 회전
- `acc_scale_err` — 크기를 1.00 / 1.03 / 1.06 / 1.10 배

얻는 것: **발산 임계 기울기**, 임계 이하 구간의 오차 증가율(완만한 열화 vs 급격한 붕괴), 실패 시 거동. 임계 이하에서는 바닥 효과가 없으므로 정량 비교도 성립한다. 두 요인을 따로 돌리므로 원인 분리도 가능하다.

**보고서 구성:** ① 하드웨어 결함 발견(이 원시 데이터가 1차 증거, 완결됨) ② 알고리즘 강건성(실패 방식은 이 데이터로, 열화 곡선은 주입 실험으로).

## 8. 분석 방법 메모

`.db3`는 SQLite이므로 `rosbag2_py` 없이 `sqlite3` + 수동 CDR 역직렬화로 파싱 가능하다. CDR 규칙: 앞 4바이트 encapsulation 헤더, 이후 각 원시 타입은 자기 크기에 맞춰 정렬, string은 `uint32 길이 + 바이트(널 포함)`.

`unitree_go/msg/LowState`의 `imu_state` 오프셋 (encapsulation 헤더 이후 기준):

| 필드 | 오프셋 | 타입 |
|---|---|---|
| quaternion | +24 | float32[4] |
| gyroscope | +40 | float32[3] |
| accelerometer | +52 | float32[3] |
| rpy | +64 | float32[3] |

`/lowstate`에는 헤더가 없어 bag 수신 시각을 써야 하며, `/utlidar/imu` 헤더 시각과 약 **−6 ~ −8 ms** 차이가 있다.

### 이번에 겪은 함정

- **좌표계 부호는 데이터 분포로 먼저 확인할 것.** 지면 평면 법선의 부호를 반대로 잡아 한동안 자이로를 범인으로 오판했다. 클라우드의 z가 전부 +0.06~+0.65에 몰려 있다는 것(= L1의 +z가 아래를 향함)을 보고서야 잡혔다. RANSAC 법선은 방향만 주고 부호는 주지 않는다.
- **서로 다른 센서를 정렬할 때는 대역폭을 맞출 것.** 6.2 참조.
- **평균과 상관은 다르다.** 두 자이로를 평균내면 잡음만 줄고 기하 정보는 생기지 않는다. 회전을 결정하는 것은 벡터쌍의 *상관*(Kabsch)이다.
- **가설이 틀렸을 때 빨리 버릴 것.** `acc_norm` +6.4% 스케일 오차는 실측으로 확정된 사실이지만 발산의 원인은 아니었다. 실측된 이상이 곧 원인이라는 보장은 없다.
